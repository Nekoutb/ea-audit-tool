# Capacity — ingestion ceiling and the 700-user question (23 Aug 2026)

## Can one upload take 500 000 lines?

**Today: CSV yes with care, XLSX no.** The honest numbers:

| Constraint | Value | Effect at 500k lines |
|---|---|---|
| Upload cap (raised today) | 60 MB (was 25 MB) | a 500k-line CSV (~40–60 MB) now fits; before today it was refused |
| Ingest write path (fixed today) | batched `unnest`, 5 000 rows/query | ~100 queries instead of 500 000 — minutes became seconds |
| CSV parsing | whole file in memory as strings | ~150–300 MB peak for 500k lines — inside the laptop's memory, tight on prod |
| XLSX parsing (ExcelJS) | full workbook DOM in memory | 500k rows ≈ several GB — **exceeds the service's 1 200 MB cap; will be killed** |
| Production service | `MemoryMax=1200M` | the real ceiling for any single ingest |

**Practical guidance:** up to ~100k lines, either format works. 100k–500k lines:
use **CSV**, not XLSX. Beyond that (or to make 500k XLSX safe) the parser needs
to become streaming (line-streamed CSV, `ExcelJS.stream.xlsx` reader) feeding
`COPY` — a contained follow-up, listed below.

Everything AFTER ingest is already sized for it: the GL projection builds in
2 000-row batches with bounded memory, and every analytic and drill-down
aggregates/paginates in SQL.

## What has to change for 700 users

Baseline: the 23 Aug load test — one Node process saturates at ~18 req/s and
queues linearly; zero errors at 150 users but 8 s medians. 700 active users at
audit-work think-times ≈ 80–100 req/s needed — **5–6× today's single-process
ceiling**.

### The current bottlenecks ("features that slow it down")

1. **One Node process.** Next.js `next start` runs a single process; every
   request shares one event loop. This is the saturation the load test
   measured. Fix: run N processes (PM2 cluster or N systemd units on ports
   3200..320N) behind the existing Apache proxy. The biggest single lever.
2. **The shared 3 vCPU / 8 GB VM.** The box also carries other businesses'
   sites, MySQL, Redis, BitNinja. 700 users deserve a dedicated 8 vCPU+ box —
   or this VM upgraded and the cluster above.
3. **Database pool per process.** The pool is sized with timeouts (Phase 0
   item 9), but N processes × pool size must stay under Postgres
   `max_connections`; at 5–6 processes add PgBouncer in transaction mode.
4. **Every page renders from live queries.** Dashboards re-run their counts on
   each visit; there is no cache. Cheap wins when needed: `unstable_cache` on
   firm-level rollups (30–60 s), and the existing per-request dedupe.
5. **Long work runs inside the request.** Large ingests, DOCX generation and
   Excel exports hold a worker for their whole duration. At 700 users these
   belong in a queue (pg-boss) with a progress endpoint — the UI groundwork
   (spinners, explicit completion states) landed today.
6. **Documents stored as bytes in Postgres.** Every download streams through
   Node from the DB. The storage boundary was built for an S3 swap
   (architecture decision #6) — do it before 700 users generate real volume.
7. **bcrypt on sign-in.** ~100 ms CPU each; fine steady-state, heavy in 9 a.m.
   login storms across 5 processes. Mitigated by the login throttle; no change
   needed until SSO.

### Ordered plan

| Step | Effort | Expected effect |
|---|---|---|
| 1. Node cluster (4–6 workers) + PgBouncer | S–M | ~4–5× throughput; the 700-user gate |
| 2. Dedicated / upgraded VM (8 vCPU, 16 GB) | infra | removes the shared-box ceiling and noisy neighbours |
| 3. Queue for ingest/exports (pg-boss) | M | long work stops blocking interactive traffic |
| 4. S3-compatible document storage | M | DB size and download path stop scaling with usage |
| 5. Streaming ingest (CSV stream + COPY, stream-XLSX) | M | 500k+ lines safely inside 1 200 MB |
| 6. Cache firm-level rollups | S | dashboard cost flattens as engagements grow |

Re-run `scripts/load-test.mjs` after each step; the 23 Aug numbers in
`docs/load-test-2026-08-23.md` are the baseline.
