# Load test — 23 August 2026

The assurance review (20 Aug 2026) scored performance 1/5 with the finding
"no load test has ever been run" and asked for 25 / 50 / 100 / 150 concurrent
users with the numbers published. This is that run.

## Method

- `scripts/load-test.mjs`: each simulated user signs in once (real browser
  sign-in, shared session) and then loops a weighted journey — dashboard,
  engagement register, clients, full-text search, notifications — with
  200–800 ms think time between pages. Every response body is fully read.
- Target: the current build (commit `bcf10a2`) served by `next start`
  (production build), PostgreSQL 16 local, dev dataset (~5 firm-A engagements).
- Hardware: the development laptop (Windows 11). The production VM is a
  3 vCPU / 8 GB Vultr instance of a similar class, but it also carries other
  workloads — a production-box run needs its own scheduled window.
- 45 seconds per level, sequential levels.

## Results

| Users | Throughput | p50 | p90 | p99 | max | 5xx / dropped |
|------:|-----------:|-------:|-------:|-------:|-------:|---:|
| 25 | 15.4 req/s | 1.1 s | 1.6 s | 2.5 s | 2.5 s | 0 |
| 50 | 17.9 req/s | 2.4 s | 3.2 s | 3.6 s | 4.2 s | 0 |
| 100 | 17.9 req/s | 5.0 s | 7.3 s | 8.2 s | 8.7 s | 0 |
| 150 | 16.8 req/s | 8.1 s | 11.8 s | 14.6 s | 15.5 s | 0 |

Every response at every level was HTTP 200. No sign-in failures, no pool
exhaustion, no 5xx, no dropped connections.

## Reading

- **The audit's fatal scenario did not occur.** C8 predicted indefinite
  queueing and an unsurvivable 100-user load against the unsized pool. With
  the pool sized and time-limited (Phase 0 item 9), the system **saturates
  and queues gracefully instead of failing**: throughput plateaus at
  ~18 req/s from 50 users up, and latency grows linearly with the queue.
- **Comfort ceiling on this hardware is ~25–50 concurrent users** (p50 1–2.4 s).
  100 users remain fully functional but slow (5 s median); 150 users are
  degraded (8 s median) yet still error-free.
- The plateau is capacity, not a defect: one Node process and one database
  share every request. The obvious levers, if the ceiling ever matters in
  production, are horizontal Node processes behind the proxy and read-path
  caching — not pool changes.

## Follow-up

- A production-box run (out of hours, with the operator's approval — the VM is
  shared with unrelated workloads) to confirm the shape on real hardware.
- Re-run after any change to `lib/db.ts` pool settings or heavy read paths,
  and when real engagement volumes exist.
